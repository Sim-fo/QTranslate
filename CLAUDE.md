# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

QTranslate is a Kotlin/Swing desktop translation tool (rewrite of the abandoned Questsoft app). Everything user-facing — translators, OCR, TTS, spell checkers, dictionaries, summarizers, rewriters — is provided by **plugins loaded from JARs at runtime**, not compiled into the app.

## Commands

Windows uses `gradlew.bat`; the Bash tool can use `./gradlew`.

```bash
./gradlew build                       # compile all modules
./gradlew :app:run -DappData="C:/path/to/test/data"   # run the app (see appData note below)
./gradlew :app:shadowJar              # fat JAR -> app/build/libs/QTranslate.jar
./gradlew :plugins:google-services:shadowJar          # plugin JAR -> plugins/<name>/build/libs/
./gradlew test                        # all tests
./gradlew :core:test --tests "*DoubleCtrlDetectorTest*"   # single test class
```

- `:app:shadowJar` is the real distributable, not `:app:jar`. Release version comes from the `APP_VERSION` env var.
- **`-DappData` matters when running from Gradle.** Without it the app resolves its data dir next to the JAR, or falls back to `%APPDATA%\QTranslate`. Two run configs sharing one `appData` dir crash DataStore ("multiple DataStores active for the same file").
- Toolchain is Java 21 for compilation; output is Java 11 bytecode. Gradle configuration cache and build cache are on (`gradle.properties`).
- `:ui-swing` and the shared convention plugin enable `-Xcontext-parameters` (context parameters are used in UI code).
- Bumping a release means changing **both** `AppConstants.APP_VERSION` (used by `CheckForUpdatesUseCase` to compare against GitHub releases) and the git tag `v<version>` that triggers `.github/workflows/release.yml`.

## Architecture

Clean Architecture + MVI. Strict one-way dependency: `:app` → `:ui-swing` → `:core` → `:api`. Plugins depend on `:api` only.

| Module | Rule |
|---|---|
| `:api` | Interfaces and data types only. Adding anything here is a public plugin-API commitment; `api/build.gradle.kts` has its own version, bumped only on API changes. |
| `:core` | Business logic, use cases, MVI stores, repositories. **No Swing imports.** |
| `:ui-swing` | Swing components implementing `Renderable<State>`. Render state, dispatch intents — no business logic. |
| `:app` | Composition root only (`Main.kt`, `AppDependencies.kt`). Keep thin. |
| `:plugins/*` | `common` holds shared HTTP/JSON/language helpers; each service plugin is a separate shadowJar. |

Full narrative in [wiki/Architecture.md](wiki/Architecture.md).

### MVI

`Store<S : UiState, I : UiIntent, E : UiEvent>` (`core/shared/arch/Store.kt`) exposes `StateFlow<S>`, a one-shot `Flow<E>`, and `dispatch(intent)`. Two stores: `MainStore` (translation screen) and `SettingsStore`. Logic lives in single-purpose use cases under `core/main/domain/usecase/`, not in the stores.

### Settings draft/commit

`SettingsStore` holds a **saved** config and a **working draft**. `UpdateDraft` mutates the draft only; `SaveChanges` persists; `CancelChanges` reverts. Nothing hits disk until save. Use `applyDraft(store) { it.copy(...) }` from settings panels to avoid stale reads.

Exception: settings that must persist immediately outside the OK/Cancel cycle (e.g. the "remember my choice" close-button preference) dispatch `ToggleSetting` + `SaveChanges` directly.

`ConfigMigrator` upgrades persisted `Configuration` field-by-field when an older config file is loaded — add migration handling there when introducing new settings fields.

### Plugins

`PluginManager` coordinates `PluginLoader` (scans `plugins/`, parses `plugin.json`, checks API version), `PluginRegistry`, `PluginLifecycleHandler` (`onInitialize` → `onEnable` → `onDisable` → `onShutdown`), `PluginInstaller`, and `PluginSettingsManager`. A plugin JAR whose hash changed since last run is held in `AWAITING_VERIFICATION` until the user confirms.

A plugin needs three things in `src/main/resources/`: `plugin.json`, `META-INF/services/com.github.ahatem.qtranslate.api.plugin.Plugin`, and its assets. Missing either of the first two is the usual cause of a plugin silently not loading.

Plugin settings UIs are **generated by reflection** from annotations on the plugin's `PluginSettings.Configurable` subclass — `@field:Setting`, `@SettingGroup(s)`, `@PluginAction` — walked by `DynamicPluginSettingsDialog`. Plugin authors write no UI code. See [wiki/Creating-a-Plugin.md](wiki/Creating-a-Plugin.md).

### Error handling

Expected failures return `Result<T, ServiceError>` (kotlin-result). `ServiceError` is sealed: `NetworkError`, `AuthError`, `RateLimitError`, `InvalidResponseError`, `UnknownError`. Throw exceptions only for genuine programming errors.

### Threading

`render()` and all Swing mutation on `Dispatchers.Swing`; network/IO on `Dispatchers.IO`; business logic on `Dispatchers.Default`. Any blocking call (`Files.copy`, DataStore, synchronous HTTP) must be wrapped in `withContext(Dispatchers.IO)`.

### Localization

All user-visible strings go through `localizer.getString("key", args...)`, resolved from TOML files in `languages/` next to the JAR. English fallback is embedded at `core/src/main/resources/localization/embedded_en.toml`. A new UI string means adding the key to `en-GB.toml` **and** the embedded fallback.

### RTL

Layout mirrors for RTL locales via `applyComponentOrientation` on the root pane. **Never use `WEST`/`EAST`/`LEFT`/`RIGHT` in layout code** — use `LINE_START`/`LINE_END`/`LEADING`/`TRAILING`. `LayoutManager.switchLayout(id, isRtl)` rebuilds the content layout on language change.

### Hotkeys

Data-driven `List<HotkeyBinding>` in `Configuration.hotkeys`. `HotkeyScope.GLOBAL` bindings register with jKeymaster (system-wide); `LOCAL` bindings are returned by `MainGlobalKeyListener.getLocalBindings()` and installed on `MainAppFrame`'s rootPane InputMap. `SHOW_MAIN_WINDOW` is special-cased: a double-Ctrl sequence detected via JNativeHook (`DoubleCtrlDetector`), not a KeyStroke.

### Cross-component messaging

`NotificationBus` (SharedFlow) carries domain notifications — e.g. `PluginManager` posts load failures — which `MainAppFrame` routes to the status bar. Do not reach into UI from `:core`; post to the bus.

## Conventions

- Conventional Commits: `<type>(<scope>): <summary>`, imperative, under 72 chars. Scopes: `core`, `api`, `ui`, `plugins`, `ci`.
- All work branches off `develop` and PRs target `develop`; never push directly to `main` or `develop`.
- The test suite is nearly empty (two classes in `:core`) — CI runs tests with `continue-on-error`. New tests use JUnit 5 + `kotlinx-coroutines-test`.
